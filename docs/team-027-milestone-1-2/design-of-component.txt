Design of Components
=====================
Team: Team 027
Project: Sangam — Student Mentoring and Career Support Platform

1. System Architecture Overview
---------------------------------
Sangam follows a layered client-server architecture with a clear separation
between the frontend SPA, the REST API backend, and the relational database.

  [Vue 3 Frontend SPA]  <--REST/JSON-->  [Django DRF Backend]  <-->  [SQLite/PostgreSQL DB]
       (Vercel)                               (Render)

State Management (Pinia Stores):
  - authStore: User session, role, JWT tokens.
  - mentorStore: Mentor directory, profiles, availability.
  - requestStore: Mentorship requests, status tracking.
  - workspaceStore: Active mentorship, goals, sessions.
  - adminStore: Verification queue, request queue, insights.
  - notificationStore: In-app notifications.

4. API Layer (REST Endpoints)
-------------------------------
Base URL: /api/v1/

Authentication:
  POST   /api/v1/auth/register/
  POST   /api/v1/auth/login/
  GET    /api/v1/auth/me/

Mentors & Discovery:
  GET    /api/v1/mentors/          (filters: domain, specialty, verified)
  GET    /api/v1/mentors/{id}/
  PATCH  /api/v1/mentors/{id}/     (availability, capacity)

Mentorship Requests:
  GET    /api/v1/requests/
  POST   /api/v1/requests/
  GET    /api/v1/requests/{id}/
  PATCH  /api/v1/requests/{id}/    (withdraw)

Availability Checks (Admin):
  POST   /api/v1/requests/{id}/check/
  PATCH  /api/v1/checks/{id}/      (mentor confirms/declines)

Mentorship & Workspace:
  GET    /api/v1/mentorships/
  POST   /api/v1/mentorships/{id}/goals/
  PATCH  /api/v1/goals/{id}/
  POST   /api/v1/mentorships/{id}/meetings/
  POST   /api/v1/mentorships/{id}/feedback/
  POST   /api/v1/mentorships/{id}/outcomes/

Admin:
  GET    /api/v1/admin/queue/
  POST   /api/v1/admin/verify/{mentorId}/
  GET    /api/v1/admin/insights/
  GET    /api/v1/admin/audit-log/

5. Data Flow (Key Workflow)
-----------------------------
1. Student registers → profile created (PENDING approval).
2. Admin approves student profile.
3. Student browses Discover Mentors, submits structured request.
4. Request enters admin queue (AI triage suggests priority).
5. Admin reviews, selects top mentor(s), sends availability check.
6. Mentor receives check, confirms within 7 days (else EXPIRED).
7. Admin approves pairing → Mentorship (ACTIVE) created.
8. Student and mentor set 1-3 goals, log sessions.
9. On completion, both give closing feedback and student records outcomes.
10. Admin monitors via programme dashboard and inactivity alerts.

6. Security & Privacy Design
-------------------------------
- Conversation content is NEVER stored on the platform.
- Session logs record date, duration, and status only.
- Audit logs record action metadata, never narrative text.
- Student profiles require IITM email domain validation.
- Mentor profiles verified by IIC admin before discoverability.
- JWT-based authentication with token blacklisting.
- Role-based permissions enforced at serializer and view level.
